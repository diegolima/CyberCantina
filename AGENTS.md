# CyberCantina Agent Guidelines

## Architecture & Context Discipline
- **Architecture Maps (`docs/architecture/`)**: Before broad grepping, consult `docs/architecture/README.md`, `docs/architecture/CROSS_LAYER_MAP.md` (FastAPI <-> frontend API endpoints, `schema.sql` ER diagram, and package file index), `docs/architecture/BACKEND_GRAPH.md`, and `docs/architecture/FRONTEND_GRAPH.md`. Regenerate after adding routes, schema tables, or modules via `backend/.venv/bin/python scripts/generate_arch_docs.py`.
- **Modular Domain Layout & Facade Seams**: Place new domain logic in the extracted subpackages rather than re-expanding compatibility facades: `backend/app/db/repos/`, `backend/app/engine/{affective,context,cognition,char_agent,clerk}/`, `backend/app/routers/campaign_routes/`, `backend/app/wizards/char_gen/`, `frontend/src/{types,api,styles}/`, and `frontend/src/components/{auth,character,chat,inspector,map,wizard,world}/`. When modifying code behind facades (`db/repository.py`, `db/vector_store.py`, `engine/{affective_engine,phase2_context,phase3_cognition,phase5_clerk,character_agent}.py`, `routers/campaigns.py`), preserve their re-exports and facade lookup hooks (`app.db.repository.embed_text`, `vs_module.embed_text`, `phase5_clerk.run_character_post_turn_agent`, `phase4_clerk`/`phase5_clerk.summarize_turn_chunk`, and `_resolve_facade_attr` in `routers/campaign_routes/schemas_and_gate.py`) so test `monkeypatch` seams remain intact. Keep layer boundaries compliant with `backend/tach.toml` (`tach check`) and `frontend/.dependency-cruiser.cjs` (`arch:check`).
- **4-Zone KV-Cache Economy**: Zone 1 static system context (`backend/app/engine/context/zone1_static.py`, re-exported via `phase2_context.py`) is paid on every turn. Keep injected character fields non-redundant and concise (strict domain boundaries between `core_persona`, `moral_code`, `quirks_flaws`, `communication_style`, `distinctive_features`, and `equipped`/`inventory`).
- **End-to-End Field Synchronization**: When changing a generated entity field's semantics or constraints (e.g., `"Height"` metric-only, single-item equipment), update all layers together: frontend form components & manual/offline fallbacks, backend prompt templates (`backend/app/prompts/defaults.py`), Pydantic schema `Field(description=...)`, backend fallback generators, and Zone 1 prompt rendering.

## LLM Integration & Post-Processing
- **Constrained JSON Schemas (Pydantic v2)**: Models with default field values emit `required: []` JSON Schemas, letting local 12B Ollama/llama.cpp models omit keys or emit blanks. Pass explicit `required_properties=list(schema_cls.model_fields.keys())` to `complete_structured` (`backend/app/engine/llm_client.py`) and model multi-line bullet outputs as `list[str]` arrays in LLM pass schemas rather than newline-delimited strings.
- **Never Shadow Multi-Pass Pipelines**: Do not pass an always-populated default prompt key (e.g., from `resolve_effective_prompts`) as an override flag into multi-pass wizard functions; doing so silently routes requests into legacy single-pass fallbacks.
- **Deterministic Hygiene Over Negative Prompts**: Do not spend prompt tokens forbidding HTML tags or formatting quirks ("never emit `<i>`"); sanitize deterministically in centralized Pydantic schema `@model_validator`s instead. Preserve functional prose formatting (e.g., convert `<i>`/`<em>` to Markdown `*...*` matching `renderFormattedProse` in `frontend/src/components/chat/chatHelpers.tsx`) while stripping raw markup from plain-text/chip fields and dropping chain-of-thought wrapper blocks (`<think>`, `<thought>`, `<reasoning>`, `<scratchpad>`). Match strict HTML tag patterns (`</?[a-zA-Z]...`) rather than greedy `<[^>]+>` so comparison operators (`Age < 30`) remain intact.
- **Genre-Adaptive Fallbacks**: Never hardcode single-genre (e.g., cyberpunk) defaults or few-shot examples in shared fallbacks; resolve defaults from multi-genre profiles and assign structured enums/presets (e.g., `BASELINE_MOOD_PRESETS`, CARE temperament) deterministically.

## Frontend UI & UX Contracts
- **Tag & Keyword Inputs**: Always use `TagChipsInput` (`frontend/src/components/TagChipsInput.tsx`) for tag/keyword arrays. Never bind `<input value={tags.join(", ")}>` with `.split(",").filter(Boolean)` in `onChange`, which deletes spaces and trailing commas on every keystroke.
- **Semantic Accents**: Reserve `--accent-rose` / red strictly for errors, validation failures, and destructive actions. Assistive AI extract/populate actions must use `--accent-amber` or `--accent-violet` with `Sparkles`.
- **Dynamic Node Modals & Creation Flows**: Keep primary `+ Add` headers sticky inside long node editors and scroll/focus newly appended entries into view. Separate catalog saving (`Save Character`) from optional session launch toggles (`Immediately start a campaign`).
- **Map Topology Editor Contracts (`v0.10.1+`)**: Keep `SpatialTopologyView` / `SpatialTopologyCanvas` deletions (`Delete` key, `"X"` quick-delete) single-snapshot Undo-backed without extra confirmation modals while surfacing `canDeleteLocation` / `canDeleteContainer` block reasons via `statusNotice`. Render hover quick-delete `"X"` controls **only** in `mode === "editor"` (`!isMutatingLocked`) on the top-right corner of distance badges (no full-line red recoloring), hide `· N` bundle suffixes when `groupedCount <= 1`, and scope map `MagicWandButton` controls (`MapDetailsDrawer.tsx`) strictly to Level 0 Locations and Level 1 (`depth === 1`) Containers (omitted on Levels 2–4).
- **Modular Stylesheets, Tokens & Primitives (`v0.29.1+`)**: `frontend/src/styles.css` is an ordered `@import` manifest (`frontend/src/styles/00-tokens.css` -> `15-responsive.css`); place new styles in the matching domain file (keeping `15-responsive.css` last), prefer semantic tokens in `00-tokens.css` and shared `.ui-*` primitives in `02-primitives.css`, align responsive rules to `620px`/`820px`/`1100px` (`campaignLayout.ts`), avoid `!important`, and consult `frontend/AGENTS.md` before styling card decks, popovers, or drawers.

## Feature Workflow, Worktrees & Specifications
- **Worktree Isolation (Required Before Edits)**: Never implement features or fixes directly on `main` unless the user explicitly instructs otherwise. Before authoring specs or editing code, create an isolated worktree under `.worktrees/<slug>/` via `scripts/worktree.sh create <slug> [prefix]` (default `feat`; bootstraps an isolated `backend/.venv` via `uv sync` and `frontend/node_modules` via `npm ci`). Keep the primary checkout parked cleanly on `main`, and always confirm your worktree path and branch (`git branch --show-current`) before editing.
- **Feature Package Gate (`docs/features/TBD-<slug>/`)**: For non-trivial features or architectural changes, create the worktree first, author `FRD.md`, `REVIEW.md`, and `PLAN.md` (plus optional `ARCHITECTURE.md`) under `docs/features/TBD-<slug>/` with `target_version: TBD`, and **stop for explicit user approval** before writing production code (unless the user explicitly says to skip the package). Small, targeted fixes (typos, minor CSS tweaks, one-line bugfixes) may skip the feature package, but still run inside a worktree branch.
- **Implementation, Verification & Review Handoff**: Perform all edits, builds, and required checks inside `.worktrees/<slug>/`. Defer edits to the shared sibling wiki (`../cybercantina-wiki`, branch `master`) until the merge step so parallel features never collide; record planned wiki pages/sections in `PLAN.md` during implementation (in-app `mechanicsCatalog.ts` updates still happen inside the worktree). Once all required checks pass, present a concise review summary (worktree path, branch, changed areas, verification results, and planned wiki updates) and wait for the user's go-ahead.
- **Commit, Merge & Push Protocol**:
  - *Commit only*: Commit on the feature branch inside `.worktrees/<slug>/` and keep the worktree open; do not modify `main`, `../cybercantina-wiki`, or push.
  - *Merge / Commit, Merge & Push* (serialize — merge one feature to `main` at a time):
    1. In `.worktrees/<slug>/`: mark the feature package `status: completed`, check off `PLAN.md`, assign the next semver and rename `docs/features/TBD-<slug>/` -> `docs/features/<semver>-<slug>/` (if present), and commit on the feature branch.
    2. Rebase onto latest `main` (`git rebase main`). If `main` moved since branching or conflicts were resolved, regenerate `docs/architecture/` and re-run the full verification suite inside the worktree before proceeding.
    3. Apply, verify (`git -C ../cybercantina-wiki diff`), and commit the planned `../cybercantina-wiki` updates.
    4. From the primary repo checkout (never `git checkout main` inside a worktree): fast-forward merge via `git -C <repo-root> merge --ff-only <branch>`.
    5. Clean up via `scripts/worktree.sh remove <slug>`.
    6. If pushing, follow **Post-Push Deployment** (push `origin main`, `github main`, and `../cybercantina-wiki`, then invoke `cybercantina-alpha-deploy`).

## User-Facing Documentation (Wiki)
- **Mandatory Wiki Updates for User-Facing Changes**: Whenever a user-facing feature (any capability, UI surface, control, workflow, command, mechanic, import/export option, or user/admin setting that a user directly interacts with) is added or modified, always add or update the relevant end-user documentation in the sibling GitHub Wiki repository (`../cybercantina-wiki`, branch `master`). Purely internal refactors, test-only changes, or backend plumbing with no user-visible change do not require wiki updates unless they alter documented behavior or setup.
- **Page Discovery & Multi-Page Sync**: Inspect `../cybercantina-wiki/_Sidebar.md` and `../cybercantina-wiki/Home.md` to identify all affected guide pages (e.g., interface tour, authoring, playing/mechanics, live inspector/map/timeline, importing/exporting, providers/models, auth/security, prompt presets, setup) and update every relevant page rather than only one. For a major new user-facing capability that does not fit an existing page, create a new hyphenated `<Page-Title>.md` page and link it in both `_Sidebar.md` and `Home.md` using GitHub Wiki link syntax (`[Title](Page-Name)` without `.md`).
- **User-Facing Scope & Separate Repo Hygiene**: Keep wiki prose practical and end-user focused (how to access, configure, and use the feature, key UI controls, and caveats); keep internal architecture specs, DDL, and task plans in `docs/features/`. Never place non-wiki files (such as `AGENTS.md`) inside `../cybercantina-wiki`, as every `.md` file there publishes as a public wiki page. In parallel worktree workflows, record planned `../cybercantina-wiki` updates in `PLAN.md` during implementation and apply/commit them at merge time with `docs: ...` commits (pushing when pushing the feature, or clearly noting any unpushed wiki changes if the sibling repo is unavailable).
- **In-App Codex Game Mechanics Sync (`v0.40.0+`)**: Whenever a user-facing mechanic changes (CARE layers/half-lives/temperaments, d20 modes/tiers, `/choice`, whispers/privacy, parties, map links/speed presets/containers, memory/Context Health, timelines/bookmarks/Major Events, GM Talk/GM Mode), update `frontend/src/components/world/mechanics/mechanicsCatalog.ts` (and `MechanicsTopicId` in `frontend/src/types/mechanics.ts` + contextual `MechanicsHelpButton` links for new topics) in sync with `../cybercantina-wiki`. Import live typed constants (`TEMPERAMENT_ARCHETYPE_OPTIONS`, `getSlashCommandSpec`, `WALKING_METERS_PER_MINUTE`, `LINK_SPEED_PRESET_GROUPS`, `CONTAINER_DEPTH_LABELS`, `PHASE_DISPLAY_META`) instead of duplicating literals, and keep `Game Mechanics` strictly static client-side reference data (never `lore_nodes`, never counted in `World Codex (N)`, never editable under GM Mode, never RAG-indexed, never exported in `.zcc`).

## Verification & Debugging
- **Character Media Path & Log Boundaries**: All character ID validation and media filesystem operations (`shutil.copytree`, `shutil.rmtree`, `FileResponse`, `unlink`, image saves) must route through `backend/app/security/media_path.py` (`validate_safe_character_id`, `safe_resolve_character_media_dir`, `safe_resolve_media_file_path`) rather than raw `Path(self.media_dir)` joins, and client-influenced log values must pass through `sanitize_log_value` (`backend/app/security/log_sanitize.py`).
- **CoW Character Media Reconciliation & `repo.media_dir` Consistency**: Any Copy-on-Write character fork or version restore (`update_character`, `restore_character_version`) must reconcile `portraits_json` and `gallery_json` URLs to `target_char_id` via `_reconcile_character_media_for_id` (and sync `portraits`/`gallery` state in `CharacterInspectorModal` on save) so pruning the old `pending_deletion` character never orphans media or drops assets from `.zcc` exports. Service-layer media helpers receiving `repo: CantinaRepository` (`import_export_service.py`) must pass `media_dir=repo.media_dir` to `safe_resolve_media_path` rather than relying on global `settings.media_dir`.
- **Live Output Diagnostics**: When debugging user-reported generation issues, inspect saved rows directly in `backend/cybercantina.db` via `sqlite3` to verify whether defects stem from LLM output, fallback imputation, or frontend rendering.
- **Frontend Vitest (Node-Only Environment)**: `frontend/package.json` runs Vitest without `jsdom` or `@testing-library/react`; keep non-DOM UI logic in pure helpers (`mapGeometry.ts`, `topologyProjection.ts`, etc.) and pair unit tests with `ReactDOMServer.renderToStaticMarkup` component assertions.
- **Required Checks Before Completion**:
  - Backend: `cd backend && .venv/bin/ruff check app tests && .venv/bin/tach check` and `backend/.venv/bin/pytest backend/tests`
  - Frontend: `npm --prefix frontend run arch:check && npm --prefix frontend run css:audit && npm --prefix frontend run build && npm --prefix frontend test`
  - Architecture docs (enforced in CI via `--check`; regenerate when modules, docstrings, routes, tables, or imports change): `backend/.venv/bin/python scripts/generate_arch_docs.py && backend/.venv/bin/python scripts/generate_arch_docs.py --check`
  - User-facing wiki docs (whenever a user-facing feature is added or modified): plan updates in `PLAN.md` during worktree implementation, then apply to all relevant pages in `../cybercantina-wiki` (plus `_Sidebar.md` / `Home.md` if adding a new page) and verify with `git -C ../cybercantina-wiki diff` at merge time.

## Post-Push Deployment
- **Dual-Remote Push & Alpha CI Watch**: This repo has both `origin` (GitLab) and `github` (`diegolima/CyberCantina`, GitHub). When pushing commits to `main`, push to both `origin main` and `github main` (GitHub Actions builds `:alpha` images from `github/main`), then—unless the user explicitly says not to deploy—invoke the `cybercantina-alpha-deploy` skill (when available) to monitor the GitHub Actions workflows for the pushed commit and restart the alpha test server once the new `:alpha` images succeed.
